# Contributing

## Philosophy

This project lives or dies on conceptual sharpness.
A bloated repo full of pretty words and mushy boundaries is worse than a smaller repo with hard edges.

---

## Contribution rules

### Add docs when they reduce ambiguity
Not to feel productive.

### Update source-of-truth files
If your change affects project state or architecture, update the right file.

### Write ADRs for durable choices
If the decision changes how the project thinks, not just how it is phrased, write an ADR.

### Prefer examples over abstractions
If a concept cannot be shown with a small example, it is probably still too vague.

---

## When to update what

### Update `MEMORY.md`
When:
- project status changes
- priorities shift
- assumptions change
- open questions change

### Update `INDEX.md`
When:
- repo navigation changes
- new source-of-truth files appear

### Update spec docs
When:
- format changes
- manifest contract changes
- semantic model changes
- CLI contract changes

### Add/update ADR
When:
- design choice is accepted and should stick

---

## Writing style

- use direct language
- avoid AI buzzword sludge
- distinguish facts from proposals
- mark v0 vs later clearly
- include tradeoffs
- include failure modes where relevant
