# Claim Schema for Agent-to-Agent Context Passing

## Problem

When agent A hands off work to agent B, context is lost. Either A dumps raw text (noisy, unverifiable) or B starts from scratch (wasteful). ARC already has content-addressed storage, selective loading, traceability, and diffing. The gap is distinguishing what kind of knowledge is being passed.

Currently, ARC claims are undifferentiated assertions extracted from source code. For agent handoff, we need to distinguish observations from decisions from open questions from blockers.

## Design: Typed Claims

Extend the existing `Claim` model with three new fields:

### New fields

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `claim_type` | string | yes | inferred from `kind` | One of: `observation`, `decision`, `uncertainty`, `dependency`, `conflict` |
| `source` | string | yes | `"builder"` | Who produced this claim. Agent ID (e.g. `"agent-a"`), `"human"`, or `"builder"` for auto-extraction |
| `timestamp` | string (ISO8601) | yes | archive `created_at` | When this claim was produced |
| `references` | list[string] | no | `[]` | IDs of other claims this claim relates to. Used by `conflict` claims to reference the two disagreeing decisions |

### Claim types

**`observation`** — A factual statement grounded in source material.

```json
{
  "id": "a1b2c3d4e5f67890",
  "claim_type": "observation",
  "text": "file auth/views.py uses session-based authentication",
  "kind": "fact",
  "source": "agent-a",
  "confidence": 0.95,
  "timestamp": "2026-04-06T14:30:00Z",
  "evidence": [{"source_unit_id": "tu-abc123", "span": [15, 42], "weight": 1.0}],
  "status": "observed",
  "references": []
}
```

Rules:
- Must have at least one evidence pointer
- Confidence is meaningful (0-1)
- Multiple agents can independently produce the same observation — dedup by content hash

**`decision`** — A judgment or recommendation made by an agent or human.

```json
{
  "id": "b2c3d4e5f6789012",
  "claim_type": "decision",
  "text": "we should migrate to JWT for stateless auth",
  "kind": "assertion",
  "source": "agent-a",
  "confidence": 0.8,
  "timestamp": "2026-04-06T14:31:00Z",
  "evidence": [{"source_unit_id": "tu-abc123", "span": [15, 42], "weight": 1.0}],
  "status": "observed",
  "references": []
}
```

Rules:
- Evidence points to what informed the decision, not what proves it
- Confidence reflects the agent's conviction, not factual certainty
- This is a lightweight decision (one-liner). For structured ADR-style decisions with options/consequences, use the existing `Decision` model

**`uncertainty`** — An open question or unknown that needs investigation.

```json
{
  "id": "c3d4e5f678901234",
  "claim_type": "uncertainty",
  "text": "unclear if rate limiting applies to /admin endpoints",
  "kind": "assertion",
  "source": "agent-a",
  "confidence": 0.0,
  "timestamp": "2026-04-06T14:32:00Z",
  "evidence": [{"source_unit_id": "tu-def456", "span": [8, 15], "weight": 0.5}],
  "status": "observed",
  "references": []
}
```

Rules:
- Confidence should be low (0.0-0.3) — it expresses how certain the agent is that this *is* an uncertainty, not the answer to the question
- Evidence points to what raised the question
- A downstream agent can resolve an uncertainty by producing an observation or decision that references the uncertainty's ID

**`dependency`** — A blocker or prerequisite for further work.

```json
{
  "id": "d4e5f67890123456",
  "claim_type": "dependency",
  "text": "this change requires updating middleware config in settings.py",
  "kind": "requirement",
  "source": "agent-a",
  "confidence": 0.9,
  "timestamp": "2026-04-06T14:33:00Z",
  "evidence": [{"source_unit_id": "tu-ghi789", "span": [1, 10], "weight": 1.0}],
  "status": "observed",
  "references": []
}
```

Rules:
- Evidence points to the code/docs that establish the dependency
- High confidence means "this definitely blocks progress"
- Can be resolved by a downstream agent producing a claim that references it

**`conflict`** — Generated by `arc merge` when two agents produce incompatible decisions.

```json
{
  "id": "e5f6789012345678",
  "claim_type": "conflict",
  "text": "conflicting decisions on auth strategy: agent-a recommends JWT, agent-b recommends OAuth2",
  "kind": "assertion",
  "source": "arc-merge",
  "confidence": 1.0,
  "timestamp": "2026-04-06T15:00:00Z",
  "evidence": [],
  "status": "contested",
  "references": ["b2c3d4e5f6789012", "f6789012345abcde"]
}
```

Rules:
- `source` is always `"arc-merge"` — generated by the merge tool, not an agent
- `references` lists the IDs of the conflicting claims
- `status` is always `"contested"`
- Not auto-resolved. A human or downstream agent must resolve by deprecating one side

## Backward compatibility

Old archives (schema_version 1.0.0) have claims without `claim_type`, `source`, `timestamp`, or `references`. On load, apply these defaults:

| Missing field | Default value | Logic |
|--------------|---------------|-------|
| `claim_type` | inferred from `kind` | `fact` → `observation`, `definition` → `observation`, `assertion` → `observation`, `requirement` → `dependency` |
| `source` | `"builder"` | Auto-extracted claims from the build pipeline |
| `timestamp` | archive `created_at` | From manifest |
| `references` | `[]` | No cross-references |

This means `arc load --type observation` on an old archive returns all `fact`, `definition`, and `assertion` claims. `arc load --type dependency` returns all `requirement` claims.

## Relationship to existing Decision model

The existing `Decision` dataclass (title, context, options, consequences, evidence, status) remains unchanged. It captures structured ADR-style decisions.

A `Claim` with `claim_type="decision"` is a lightweight decision — a one-liner judgment.

When filtering with `--type decision`:
- Returns all claims where `claim_type == "decision"`
- Also surfaces existing `Decision` objects in the output (they are inherently decisions)

## Query interface

New CLI flags on `arc load`:

```bash
# Filter by claim type
arc load archive.arc --type observation
arc load archive.arc --type decision
arc load archive.arc --type uncertainty
arc load archive.arc --type dependency

# Filter by source
arc load archive.arc --source agent-a
arc load archive.arc --source human

# Compose filters (AND logic)
arc load archive.arc --type decision --source agent-a

# Combine with existing task-based filtering
arc load archive.arc --task "auth migration" --type decision
```

## Storage

No new layers required. Typed claims are stored in the existing `semantic.claims` layer. The new fields are additional keys in each claim's JSON object within the blob.

The `semantic.decisions` layer continues to store the rich `Decision` model separately.

## Schema version

Archives using typed claims use `schema_version: "1.1.0"`. Loaders at 1.0.0 ignore unknown fields, so forward compatibility is safe. Loaders at 1.1.0 apply the backward-compat defaults when loading 1.0.0 archives.

## What this enables

With typed claims and source tracking, ARC supports:

1. **Sequential handoff**: Agent A builds `review.arc` with observations and decisions. Agent B loads it, filters to decisions, acts on them, produces `fixes.arc` with new observations referencing A's decisions.

2. **Parallel merge**: Agents C and D work independently. `arc merge` combines their artifacts, flags conflicts where both made incompatible decisions about the same topic.

3. **Audit trail**: Every claim traces back to its source agent and through evidence pointers to original source code. You can answer "why does agent B think we should change this?" by following the chain.

4. **Selective loading**: A downstream agent only needs decisions? Load just decisions. Only care about what agent A found? Filter by source. This keeps prompt context lean.

## Open questions (to resolve during implementation)

1. **Conflict detection in merge**: How do we determine two decisions conflict? Text similarity? Same evidence pointers? Same topic extracted from heading context? Start simple: flag decisions from different sources with cosine similarity > 0.8 on their text embeddings.

2. **Resolution tracking**: When a conflict or uncertainty is resolved, how is that recorded? Proposal: the resolving agent produces a new decision claim with `references` pointing to the resolved conflict/uncertainty, and the original claim's status is updated to `deprecated` in the merged archive.

3. **Claim type for existing `kind` values**: The mapping (fact→observation, etc.) is lossy. Should we keep `kind` as a sub-category? Yes — `claim_type` is the coarse category, `kind` is the fine-grained label. Both are queryable.
