# ARC Context Passing Protocol

ARC is a protocol for passing structured, verifiable context between AI agents. When agent A hands off work to agent B, ARC ensures B receives not just text, but typed claims with provenance — traceable back to source code, with Merkle integrity guarantees.

This document is for anyone building an agent framework who wants to integrate ARC as the context layer.

## What is an ARC artifact?

An `.arc` artifact is a single SQLite file containing all context, metadata, and integrity seals:

```sql
-- Two tables inside project.arc (SQLite)
blobs(digest TEXT PRIMARY KEY, data BLOB, size INTEGER)  -- content-addressed layers
meta(key TEXT PRIMARY KEY, value TEXT)                     -- manifest, provenance, metadata
```

A legacy directory-based format is also supported (`open_cas()` auto-detects). See [`docs/single-file-format.md`](single-file-format.md) for the design.

**Key properties:**
- **Single file**: one `.arc` you can commit, share, attach to tickets
- **Content-addressed**: every blob stored by SHA-256 digest
- **Random access**: look up any blob by digest via indexed query — no unpacking
- **Merkle-sealed**: `root_digest` covers the entire manifest, making tampering detectable
- **Offline-verifiable**: no network needed to check integrity

## Claims

Claims are the atomic unit of context in ARC. Each claim is a typed assertion with provenance.

### Claim types

| Type | Purpose | Example |
|------|---------|---------|
| `observation` | Factual statement grounded in source | "auth/views.py uses session-based authentication" |
| `decision` | Judgment made by an agent or human | "we should migrate to JWT for stateless auth" |
| `uncertainty` | Open question needing investigation | "unclear if rate limiting applies to /admin endpoints" |
| `dependency` | Blocker or prerequisite | "this change requires updating middleware config" |
| `conflict` | Merge artifact — two agents disagree | Generated by `arc merge`, never by agents directly |

### Claim fields

```json
{
  "id": "a1b2c3d4e5f67890",
  "text": "auth/views.py uses session-based authentication",
  "kind": "fact",
  "claim_type": "observation",
  "source": "agent-a",
  "timestamp": "2026-04-06T14:30:00Z",
  "evidence": [
    {
      "source_unit_id": "tu-abc123",
      "span": [15, 42],
      "weight": 1.0
    }
  ],
  "confidence": 0.95,
  "status": "observed",
  "references": [],
  "derived_from": "tu-abc123"
}
```

| Field | Type | Description |
|-------|------|-------------|
| `id` | string | Unique identifier (content-hashed or UUID) |
| `text` | string | The claim content |
| `kind` | string | Fine-grained label: fact, assertion, requirement, definition |
| `claim_type` | string | Coarse category: observation, decision, uncertainty, dependency, conflict |
| `source` | string | Who produced this: agent ID (e.g. "agent-a"), "human", or "builder" |
| `timestamp` | string | ISO8601 when the claim was produced |
| `evidence` | array | Pointers to source units that support this claim |
| `confidence` | float | 0.0–1.0. For observations: factual certainty. For decisions: conviction |
| `status` | string | observed, derived, verified, deprecated, contested |
| `references` | array | IDs of related claims. Conflict claims reference the two disagreeing claims |
| `derived_from` | string | Source unit ID for simple provenance |

### Guidelines by type

**Observations**: Must have evidence pointers. Confidence reflects factual certainty. Multiple agents can independently observe the same thing — deduplication is by content hash.

**Decisions**: Evidence points to what informed the decision, not what proves it. Confidence reflects the agent's conviction. For lightweight judgments, use a claim with `claim_type: "decision"`. For structured decisions with options and consequences, use the separate `Decision` model.

**Uncertainties**: Confidence should be low (0.0–0.3). Evidence points to what raised the question. A downstream agent resolves an uncertainty by producing an observation or decision that references it.

**Dependencies**: Evidence points to code/docs establishing the dependency. A downstream agent can resolve by referencing the dependency in a new claim.

**Conflicts**: Generated only by `arc merge`. Source is always "arc-merge". Status is always "contested". References list the two conflicting claim IDs.

## Producing artifacts

### Full build: `arc build`

Builds an archive from a source directory.

```bash
arc build ./src --out review.arc                    # rule-based extraction
arc build ./src --out review.arc --extract-with-llm # LLM-assisted (richer claims)
```

**Rule-based (default):** regex pattern matching, signature claims for all functions, class summaries. Deterministic, no API key needed. Claims have `source: "builder"`.

**LLM-assisted (opt-in):** sends full files to LLM for comprehensive claims covering error handling, cross-function flow, exceptions. Claims have `source: "llm-extracted"`. Requires API key.

### Snapshot: `arc snapshot`

Creates a lightweight subset of an existing archive. Useful for quick handoffs.

```bash
# Last 10 claims
arc snapshot full.arc --out handoff.arc --last 10

# Only decisions from a specific agent
arc snapshot full.arc --out decisions.arc --type decision --source agent-a
```

A snapshot is a valid `.arc` artifact: same format, same Merkle integrity, loadable by the same `arc load` command. It contains only the selected claims, their referenced source units, and a minimal embeddings index.

Snapshots link back to their parent via `parent_archive` in the manifest. Claims are content-addressed, so snapshot claims are findable inside the parent archive.

### Programmatic creation

Agents can create claims directly and package them:

```python
from arc.models import Claim, EvidencePointer

claim = Claim(
    text="should migrate to JWT for stateless auth",
    claim_type="decision",
    source="my-agent",
    timestamp="2026-04-06T14:30:00Z",
    confidence=0.85,
    evidence=[EvidencePointer(source_unit_id="tu-123", span=(15, 42))],
)
```

## Consuming artifacts

### Load: `arc load`

Load an archive and optionally filter its contents.

```bash
# Load everything
arc load review.arc

# Filter by claim type
arc load review.arc --type decision

# Filter by source agent
arc load review.arc --source agent-a

# Combine filters
arc load review.arc --type decision --source agent-a

# Task-based selective loading (uses embeddings)
arc load review.arc --task "auth migration"

# Combine task filtering with type/source
arc load review.arc --task "auth migration" --type decision
```

### Programmatic loading

```python
from arc.loader import load

# Load with filters
loaded = load("review.arc", claim_type="decision", source="agent-a")

# Access claims
for claim in loaded.claims:
    print(f"[{claim.claim_type}] {claim.text}")
    print(f"  source: {claim.source}, confidence: {claim.confidence}")
    for ep in claim.evidence:
        print(f"  evidence: {ep.source_unit_id} lines {ep.span}")

# Also access structured decisions
for dec in loaded.decisions:
    print(f"Decision: {dec.title}")
    print(f"  Context: {dec.context}")
    print(f"  Chosen: {dec.decision}")
```

## Merging artifacts

When two agents work in parallel, merge their outputs:

```bash
arc merge security.arc performance.arc --out combined.arc
```

### Merge rules

1. **Observations coexist.** Both agents' observations are valid and included.
2. **Duplicates are deduplicated.** Same text → same claim. Content-addressed.
3. **Conflicting decisions are flagged.** If two agents make decisions with similar text from different sources, a `conflict` claim is created that references both. The conflict is not auto-resolved.
4. **Resources and source units merge.** Deduplicated by ID.
5. **Merkle integrity is maintained.** The merged archive has its own valid root digest.

### Conflict resolution

Conflicts appear as claims with `claim_type: "conflict"` and `status: "contested"`. A human or downstream agent resolves by:

1. Loading the merged archive
2. Filtering to conflicts: `arc load combined.arc --type conflict`
3. Reading the `references` field to find the two disagreeing claims
4. Producing a new decision that supersedes one or both

## Verification

```bash
# Verify archive integrity
arc verify review.arc

# Compare two archives
arc diff review.arc fixes.arc
```

### What verification guarantees

- **Blob integrity**: Every blob's SHA-256 digest matches its content. Tampering is detectable.
- **Manifest integrity**: The `root_digest` covers the entire manifest. Any modification to layer references, archive ID, or version is caught.
- **No missing blobs**: Every layer referenced in the manifest has a corresponding blob.
- **Offline**: No external service needed. Everything verifiable from the archive alone.

### What verification does not guarantee

- **Claim correctness**: An agent can produce wrong observations. Verification proves the artifact wasn't tampered with, not that its contents are true.
- **Source authenticity**: Without signatures (not yet implemented), you can't prove who built the archive. The `source` field is self-reported.

## CLI reference

| Command | Purpose |
|---------|---------|
| `arc init [dir] [--json]` | Detect project, generate config, build first `.arc` |
| `arc build <dir> --out <path> [--extract-with-llm]` | Build `.arc` (rule-based or LLM-assisted) |
| `arc snapshot <archive> --out <path> --last N` | Create lightweight snapshot |
| `arc merge <a> <b> --out <path>` | Merge two archives |
| `arc load <archive> [--type T] [--source S] [--task Q] [--full]` | Load and query archive |
| `arc inspect <archive>` | Display archive metadata and layers |
| `arc verify <archive>` | Verify archive integrity |
| `arc diff <a> <b>` | Compare two archives |
| `arc restore <archive> --out <dir>` | Restore source files from archive |

## Patterns

### Sequential handoff

```
Agent A: Review codebase
  → build/snapshot review.arc (observations + decisions + uncertainties)
  → hand review.arc to Agent B

Agent B: Load review.arc
  → filter to decisions: load(review.arc, claim_type="decision")
  → act on decisions, produce fixes.arc
  → fixes.arc claims reference review.arc claim IDs via `references` field

Audit: trace any fix back through the decision to the original observation to source code
```

### Parallel work + merge

```
Agent C: Review security → security.arc
Agent D: Review performance → performance.arc

merge(security.arc, performance.arc) → combined.arc
  → observations from both coexist
  → conflicting decisions flagged as conflict claims
  → downstream agent loads combined.arc, resolves conflicts
```

### Incremental context accumulation

```
Session 1: arc build ./src --out v1.arc
Session 2: arc build ./src --out v2.arc --parent v1.arc
Compare:   arc diff v1.arc v2.arc
```

## Design principles

1. **Artifact-first.** Context is a verifiable artifact, not runtime state. Build once, load many times.
2. **Content-addressed.** Same content → same hash. Deduplication and subset detection are free.
3. **Typed claims.** Not raw text. Every piece of context has a type, source, confidence, and evidence.
4. **Selective loading.** Load only what you need. Filter by type, source, or semantic relevance.
5. **Offline verification.** No external services. Check integrity from the archive alone.
6. **Composable.** Build, snapshot, merge, load, diff, verify. Each command does one thing.
